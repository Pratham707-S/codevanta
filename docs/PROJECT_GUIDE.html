Product · Architecture · CLI · Team execution

Fix with evidence.
Verify before trust.

RepoGuard is planned as a CLI-first AI software reliability assistant. It helps developers understand a repository, investigate risks, propose repairs, verify changes in a controlled workspace, and preserve evidence of what happened.

CLI-firstNode.js + TypeScript proposedHuman-approved editsFour-person teamEvidence-led
Read this status carefully: RepoGuard was intentionally left empty while architecture decisions are being made. This guide describes the target design. Commands, folders, and features are not implemented until code and tests prove they work. The immediate goal is one small, reliable end-to-end MVP—not all 15 features at once.
01

Problem and product promise

Problem

Tools and evidence are fragmented

Developers switch between code review, static analysis, AI chat, test logs, runtime alerts and GitHub changes. Important context is scattered.

Problem

An AI patch is not proof

A plausible suggestion can still break behavior. Generated, applied and verified are separate states and must never be reported as the same thing.

Promise

One inspectable workflow

Connect scan → evidence-backed finding → patch proposal → verification → final report, while the developer stays in control.

Long-term vision

Reuse verified outcomes

Later, store successful and failed repair evidence to help identify similar risks in authorized connected repositories.

Pitch: “RepoGuard turns code analysis and proposed fixes into a continuous, evidence-backed workflow—from a developer’s terminal to safer changes across connected repositories.”
02

How the CLI works in a terminal

The CLI is the developer’s local interface. It discovers the current project, applies safe file rules, calls analysis/repair workflows, and prints results. AI does not magically become functional just because a config file exists: every command must be implemented and connected to a real workflow.

# From inside an existing project (proposed commands)
npx repoguard init
npx repoguard scan
npx repoguard review
npx repoguard findings
npx repoguard fix FINDING-001
npx repoguard test REPAIR-001
npx repoguard status SCAN-001
npx repoguard config

These command names are proposals. Confirm the package name and command contract before implementation; do not advertise them as working until tested.

init
Setup
Purpose

Detect project root, explain what RepoGuard will read, and create a minimal config only after approval. Never inject imports into application source files.

Output

Config path, detected project, exclusions and next command.

scan
Analyze
Purpose

Discover supported files, ignore dependencies/generated content/secrets, build bounded context, and run configured analysis.

Output

Scan ID, progress, findings count and report location.

review / findings
Purpose

Show severity, path/line evidence, explanation, confidence/uncertainty and suggested next steps.

Output

Evidence must be distinguished from AI hypotheses.

fix FINDING-ID
Purpose

Create a targeted patch tied to one finding. Default to displaying a diff; modifying project files requires explicit approval.

Output

Repair ID, changed paths, rationale and patch status.

test REPAIR-ID
Purpose

Run only approved checks against the candidate patch in a disposable controlled workspace.

Output

Actual command, exit code, duration, bounded output and pass/fail/not-run status.

status SCAN-ID
Purpose

Read the real run state from local records in a local-only MVP, or persistent storage if a hosted backend is later justified.

config
Purpose

Show validated settings and safe diagnostics without printing credentials. AI calls need a supported provider adapter and valid credentials.

Key distinction: config setup is not implementation. It does not automatically provide repository scanning, model calls, repair generation, sandbox verification, GitHub access or any of the 15 capabilities.

CLI layer

Argument parsing, prompts, command routing, exit codes and readable terminal output.

Application layer

Coordinates scan/review/repair/test use cases and maps failures to stable results.

Intelligence layer

File filtering, context building, AI adapter and output schema validation.

Repair and verification

Diff generation, approval gate, temporary workspace, allowlisted checks and evidence.

Hosted architecture — later only

CLI → authenticated API → queue/worker → analysis/repair → isolated sandbox → persisted evidence → approved GitHub PR. GitHub automation needs an authorized GitHub App, least-privilege permissions, commit-SHA pinning and webhook signature verification. An npm CLI by itself cannot perform a complete remote PR workflow.

What each major area owns

cli/ — user interface OWNER: TEAM LEAD

Parses commands and flags, prints useful output, and calls application use-cases. It should not contain scanning or AI business logic.

application/ + domain/ — workflow and contracts OWNER: TEAM LEAD

Use-cases coordinate the steps. Domain types define stable contracts for findings, evidence, repair proposals, and verification results so team members can work without inventing incompatible shapes.

repository/ + context/ — understand the codebase safely OWNER: MANNI

Discover the repository, honor ignore rules, read bounded source files, inspect Git state, rank relevant context, and redact secrets before anything is sent to an AI provider.

analysis/ + providers/ — investigate and normalize AI output OWNER: TEAM LEAD

Agents investigate bugs/security/performance. Provider adapters isolate model APIs. All model output must be schema-validated and findings must reference evidence; AI claims are not automatically facts.

repair/ + verification/ — propose, approve, verify OWNER: PRATHAM

Build a diff, validate paths and patch shape, show the user what would change, require approval before applying, then run only policy-approved checks with timeouts and report the actual result.

storage/ + memory/ — state and learning AYAN / LATER

Storage persists local runs/findings. Later, memory can retain scoped, privacy-aware lessons from verified successful and failed repairs. Do not add a vector database before a tested retrieval need exists.

integrations/github/ + telemetry/ — later integrations LATER

GitHub PR creation requires explicit authorization and permission checks. Telemetry-driven rollback/self-healing is a later, high-risk capability and must not be implied by the initial CLI.

01 · MVP

Repository / GitHub analysis

Inspect local repositories first; later add authorized GitHub ingestion pinned to a commit SHA. Exclude irrelevant and sensitive files.

Security, bug and performance investigation

Run focused analysis passes. These may be functions/prompts initially, not separate autonomous services.

RAG and persistent AI memory

Retrieve relevant code and verified outcomes. Start with simple searchable records; add vector search only if measured retrieval quality needs it.

AI repair engineer

Generate a targeted, reviewable diff tied to a finding, with a rationale and changed-path list.

05 · MVP safety

Sandbox verification

Run approved checks in a disposable workspace with time/resource/output limits and captured results.

06 · Next

Learn from successful and failed fixes

Store exact patch identity, test evidence and failure reasons so future attempts can reuse real outcomes.

07 · Next

Authorized GitHub pull requests

Create a PR only with explicit permissions and approval. A PR is not proof the fix works.

08 · Next

Root-cause timeline

Link scan, finding, patch, test run and commit into an inspectable event history.

09 · Later

Regression and side-effect prediction

Suggest affected paths and regression tests; treat predictions as hypotheses until validated.

10 · Later

Repository knowledge graph

Represent imports/calls/ownership to trace impact. Start with a basic dependency map if sufficient.

11 · MVP report, improve later

Evidence-based repair confidence

Use explainable evidence coverage, patch validity and test outcomes. Model self-confidence is not proof.

12 · Safety

Human approval and safe auto-repair

Require review before edits or PRs. Future automation needs explicit policy, scope and recovery limits.

13 · Later

Future bug predictor

Estimate risk only after building a suitable dataset and measuring prediction quality.

14 · Later

Telemetry-driven rollback / recovery

Correlate release signals and propose recovery. A revert PR is not the same as live rollback or undoing a database migration.

15 · Later vision

Cross-repo ripple memory and proactive immunization

A verified fix in Repo A becomes scoped memory; search authorized Repo B/C for similar patterns and suggest a preventive test or patch. Prove it with two fixture repos before broader claims.

Long-term headline: “Fix once. Protect connected repositories.” This is a vision statement, not a claim that the cross-repo system already works.

Roadmap: now, next, later

Build in order. Each phase begins only after the previous acceptance test works.

Phase 0 — Lock architecture

Agree on scope, stack, command contract, finding schema, module boundaries, four owners and safety rules.

Exit: team sign-off

Phase 1 — CLI skeleton and safe scan

Help/version, project-root detection, config validation, file filtering, ignore rules, size limits and deterministic scan report. No AI needed yet.

Exit: scanner tests pass

Phase 2 — One AI analysis pass

Provider interface, mock provider, bounded context and schema-validated findings with code evidence. Support one language first.

Exit: fixture findings reproducible

Phase 3 — Patch proposal and verification

Generate a diff, require approval to apply, run allowlisted checks in a controlled temporary workspace, and report actual results.

Exit: known-bug fixture validates the flow

Phase 4 — Evidence records and retrieval

Store scan/finding/patch/test outcomes; learn from failures. Add RAG/vector search only after retrieval evaluation.

Exit: evidence reusable

Phase 5 — GitHub integration

Authorized GitHub App, least privilege, pinned commit SHA, webhook validation and human-approved PRs.

Exit: PR includes tested-patch evidence

Phase 6 — Cross-repo prevention

Use a verified-fix memory to find similar patterns in two authorized fixture repositories and suggest a preventive test.

Exit: repeatable two-repo demo

Phase 7 — Telemetry and prediction research

Investigate regression estimates, production signals and recovery simulations only after the core workflow is reliable.

10

Security and trust rules

Repository content is untrusted

Source files can contain prompt injection, secrets, huge generated blobs or hostile scripts. Do not treat repository text as trusted instructions.

Credentials stay private

Use environment variables/secure storage. Never commit `.env`, tokens or keys; never print credentials in logs or config output.

Execution has boundaries

Use command allowlists, timeouts, resource limits, restricted filesystem access and disposable workspaces. Never mount a host Docker socket into an untrusted sandbox.

External actions require approval

PR creation and production recovery need scoped permissions and approval. A revert PR is not the same as live rollback or undoing a database migration.

11

Demo story and acceptance checklist

Prove one real behavior rather than showing a large folder tree or an AI chat mock-up.

Demo sequence
  1. Open a tiny fixture repository containing a known bug.
  2. Run the implemented RepoGuard CLI command.
  3. Show finding, evidence, file path and line range.
  4. Generate a patch proposal and inspect the diff.
  5. Show the known check failing before the fix, where applicable.
  6. Run verification against the exact proposed patch in a controlled workspace.
  7. Show real output, exit code and final status.
  8. Prove the original working tree was not silently changed.
  • Help and clean setup work in the agreed environment.
  • Empty repo and invalid config give understandable results.
  • Secret and ignored files are excluded.
  • Malformed model output and provider errors fail safely.
  • Patch is reviewable and linked to a finding ID.
  • Verification status matches the real result.
  • README documents only commands that currently work.
  • Each member can explain their module and interface.

Checklist state is local to this browser and is not saved to GitHub.
